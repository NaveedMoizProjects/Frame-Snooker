# Scoring / Foul / Hitting-Accuracy Audit

Generated by reading `GameManager.cs` (foul + scoring code) and `Cue.cs` (strike +
aim-prediction code) line by line and comparing against real World Snooker rules.
Each item is marked:

- ✅ **OK** — matches real rules, no change needed
- ⚠️ **GAP** — not implemented / simplified, working as intended for now but flagged
- 🐞 **BUG** — behaves incorrectly vs. real rules, should be fixed

---

## A. Scoring logic (`EvaluateFoul`, `EvaluateShotResult`, `AwardPoints`)

| # | Rule | Status | Notes |
|---|---|---|---|
| A1 | Red = 1, Yellow = 2, Green = 3, Brown = 4, Blue = 5, Pink = 6, Black = 7 | ✅ OK | `BallValue` dictionary matches exactly. |
| A2 | Multiple reds potted legally in one shot each score 1 | ✅ OK | `redsPotted` loop in `EvaluateFoul`'s Red branch counts every red potted. |
| A3 | Potting a nominated colour scores its value, player continues on Red next | ✅ OK | Legal colour branch awards `BallValue[target]`; `ResolveColourPot` respots it and flips back to `Red` state if reds remain. |
| A4 | Legal pot → same player continues (no turn pass) | ✅ OK | `AwardPoints` is called without `PassTurn()` in the legal branch. |
| A5 | Miss (legal shot, nothing potted) → turn passes, 0 points | ✅ OK | `legal && points == 0` branch calls `PassTurn()` only. |
| A6 | Once reds are gone, colours are potted strictly in Yellow→Green→Brown→Blue→Pink→Black order | ✅ OK | `ColourSequence` + `AdvanceColourSequence()`. |
| A7 | Re-spotting: a potted colour (while reds remain) goes back on its own spot, not some other spot | ✅ OK, with a documented simplification | `ResolveColourPot` respots to `BallIdentity.SpawnPosition` always — real rules require the *nearest available spot up the table* if the ball's own spot is occupied. Code's own comment already flags this as "assumed, rare edge case." Leave as-is unless two colours frequently collide on respot in your table layout. |
| A8 | **End-of-frame / respotted black tie procedure** | ⚠️ GAP | When `colourSequenceIndex` runs past `Black`, code just logs `"Colour sequence complete"` and stops — no actual frame-end state, no re-spot-black-on-a-tie handling. Fine if you don't need full frame completion yet, but this is the actual "game over" moment and currently does nothing user-visible (no winner announced). |
| A9 | **Free ball after an opponent's foul** | ⚠️ GAP | Not implemented at all. Real rules: after a foul that leaves the incoming player unable to hit the ball on directly, they may nominate any ball as a "free ball." This is a meaningful rules gap if you want tournament-accurate play — currently the next player is simply still "on Red"/"on Colour" as normal regardless of how bad the foul left them. |

## B. Foul logic (`EvaluateFoul`)

| # | Rule | Status | Notes |
|---|---|---|---|
| B1 | Minimum foul penalty = 4 points | ✅ OK | `Mathf.Max(4, ...)` applied everywhere a foul awards points. |
| B2 | Foul penalty = value of ball on, ball first hit, or ball(s) potted — whichever highest | ✅ OK (simplified) | Code picks *one* relevant value per branch (first-ball-hit value, or highest illegally-potted value) rather than computing the true max across all three categories simultaneously. In the vast majority of real scenarios these coincide; a rare case (e.g., first ball hit is Blue(5) but a Black(7) also gets potted illegally) — check: `AnyNonRedPottedThisShot()` path does use `HighestValuePottedIllegally()` which would correctly pick 7 there. Looks correctly handled on inspection. ✅ upgraded to OK. |
| B3 | Cue ball potted = foul, penalty = max(4, value of ball on) | ✅ OK | `cueBallPotted` check in both branches. |
| B4 | Hitting nothing = foul, same penalty rule as B3 | ✅ OK | `firstBallContacted == null` handled identically to potted-cue-ball. |
| B5 | Hitting the wrong ball first = foul, penalty = max(4, value of ball actually hit) | ✅ OK | `firstType != Red` / `firstType != target` branches. |
| B6 | Potting a colour while on Red = foul | ✅ OK | `AnyNonRedPottedThisShot()`. |
| B7 | Potting anything other than exactly the nominated colour while on Colour = foul | ✅ Fixed | The else-branch used to catch "potted nothing" too, so hitting the right colour and missing was a foul. That is now a legal miss (`PottedThisShot.Count == 0`), and only a wrong or extra ball potted is a foul. |
| B8 | **Touching the cue ball twice in one strike ("push shot")** | ⚠️ GAP | Not detectable with the current architecture (`CueBallContactTracker` only tracks the *first* ball-to-ball contact, not cue-to-cue-stick re-contact). Genuinely hard to detect physically without extra cue-tip tracking — reasonable to leave unimplemented unless you're going for full rules accuracy. |
| B9 | **Cue ball jumping/leaving the table surface** | ⚠️ GAP | No trigger/volume detects the cue ball going airborne off the table. Currently a physically-launched cue ball would just... fly and land back on the table or fall through if there's no floor collider below table height. Worth adding a simple "if ball's Y position drops below table height, treat as foul + respot" safeguard even if not from a real jump-shot mechanic. |
| B10 | Player who commits foul still can't be "on" that ball afterward if it's the free-ball scenario | ⚠️ GAP | Same as A9 — free ball not implemented, this is the mechanical consequence of that gap. |
| B11 | Foul always passes the turn | ✅ OK | Every foul branch calls `PassTurn()`. |

**Summary: no outright scoring/foul BUGS found on inspection — the core point/foul math is correct.** The gaps (A8, A9, B8, B9, B10) are all *missing advanced rules*, not incorrect implementations of the rules that do exist. Prioritize A8 (frame doesn't actually end) and B9 (no off-table detection) if you want a genuinely completable, unexploitable game; A9/B8/B10 (free ball, push shots) are optional polish for full tournament accuracy.

## C. Hitting accuracy (`Cue.cs` — aim prediction & strike)

| # | Check | Status | Notes |
|---|---|---|---|
| C1 | Aim line uses correct sweep radius for the cue ball when predicting contact | ✅ OK | `Physics.SphereCast(currentOrigin, cueBallRadius, ...)` — radius correctly read from the ball's `SphereCollider` at `Start()`. |
| C2 | Ghost-ball (contact point) position is geometrically correct | ✅ OK | `origin + currentDir * ballHit.distance` is exactly where the swept sphere touches — correct. |
| C3 | Object-ball travel direction after contact | ✅ OK (standard simplification) | `Flat(-ballHit.normal)` is the correct centre-to-centre line for a stun/plain hit. Real physics adds a small "throw" deviation from friction/spin at contact, which this doesn't model — acceptable for an aim-assist line, not for the actual physics simulation (see C6). |
| C4 | Cue-ball deflection direction after contact (the "90° rule") | ✅ OK (standard simplification, correctly implemented) | `currentDir - Vector3.Project(currentDir, objDir)` is exactly the tangent-line formula for an equal-mass elastic collision with no spin. Correctly goes to ~zero on a dead-centre hit (stun shot) — that's real physics, not a bug. Does **not** account for side-spin (English) bending this line, which is expected since `angleOffsetDegrees`/`verticalAngleDegrees` aren't fed into the prediction math at all (see C7). |
| C5 | Cushion bounce prediction (dashed line reflecting off rails) | ✅ OK | `Vector3.Reflect(currentDir, railHit.normal)`, capped by `maxReflectionBounces`, loop correctly decrements `remainingDistance` and terminates — no infinite-loop risk. |
| C6 | **Actual strike physics vs. the predicted line matching** | ⚠️ GAP | The prediction line is a simplified straight-line/tangent model; the *actual* physics (Rigidbody collisions + `BallRollingFriction` + spin torque) can diverge from it, especially with English/spin applied (`applySpinTorque`), since curve-off-spin isn't in the prediction math at all. This is normal for pool/snooker games (perfect real-time trajectory prediction with spin is genuinely hard) — flagging so it's a known, accepted gap rather than a surprise when the ball doesn't land exactly on the drawn line. |
| C7 | English/spin (`angleOffsetDegrees`, `verticalAngleDegrees`) affects the actual strike but not the aim-prediction line | ⚠️ GAP | Confirmed by reading `GenerateAimPrediction()` — it always uses the raw `dir` from stick-to-ball, never calls `CalculateForceDirection()`. So when a player dials in side-spin, the white/red prediction lines don't reflect the curved shot they're about to hit. Cosmetic/UX gap, not a physics bug — the strike itself does use `CalculateForceDirection()` correctly (`ApplyForceToCueBall`). |
| C8 | Strike force scaling is consistent and not double-applied | ✅ OK | Single multiplication: `GameManager.baseStrikeForce * Cue.forceMultiplier`, and the code comment explicitly warns not to tune both at once — no duplicate scaling found. |
| C9 | Spin torque magnitude is reasonable relative to strike force | ✅ OK, arbitrary tuning constant | `spinMagnitude = finalForceMagnitude * 0.1f` — a fixed 10% fraction, no bug, just a "tune by feel" constant worth play-testing. |
| C10 | Cushion contact affecting the cue ball mid-flight — already covered | ✅ FIXED | See `CUSHION_PHYSICS_FIX.md` — this was the actual reported bug and is now fixed at the code level, pending the Inspector `Ball Layer` setup described there. |

## Net result: what actually needs code changes vs. what's just Inspector setup

**Needs code changes (real gaps, ranked by impact):**
1. Frame doesn't end (A8) — no winner/game-over state when colours run out.
2. No off-table/airborne cue-ball detection (B9).
3. Aim-prediction line ignores spin (C7) — cosmetic but affects player trust in the aim line.
4. Free ball rule missing (A9/B10) — only relevant if you want full tournament rules.
5. Push-shot detection (B8) — hard to do properly, lowest priority.

**Needs Inspector/scene setup, not code (already covered in `CUSHION_PHYSICS_FIX.md`):**
- Cushion `Ball Layer` assignment
- Ball Rigidbody `Drag`/`Collision Detection` settings

**No bugs found in the core scoring/foul math itself** — it correctly implements the
subset of snooker rules it claims to implement (see §A/§B tables above).
